1.2 Pasos 1–6: Scripts de carga — Resultado modelo

El script completo está en labs/data/lab07/W07_carga.sql. Los puntos críticos a verificar:

Paso 2 — proveedores

LOAD DATA LOCAL INFILE '/ruta/a/proveedores.csv'
    INTO TABLE proveedores
    CHARACTER SET utf8mb4
    FIELDS TERMINATED BY ',' OPTIONALLY ENCLOSED BY '"'
    LINES TERMINATED BY '\n'
    IGNORE 1 ROWS
    (proveedor_id, nombre_proveedor, rut, contacto, email, telefono);

El listado explícito de columnas garantiza que el mapeo sea correcto independientemente de si el grupo tiene columnas adicionales en su diseño.

Paso 4 — despachos (manejo de NULL)

El uso de @variable + NULLIF es el punto más técnico del laboratorio. Tres fechas pueden ser NULL (despachos en estado Pendiente o En tránsito sin entrega confirmada):

LOAD DATA LOCAL INFILE '/ruta/a/despachos.csv'
    INTO TABLE despachos
    ...
    (venta_id, direccion_entrega, @fecha_despacho, @fecha_entrega_estimada, @fecha_entrega_real, estado)
SET
    fecha_despacho          = NULLIF(@fecha_despacho, ''),
    fecha_entrega_estimada  = NULLIF(@fecha_entrega_estimada, ''),
    fecha_entrega_real      = NULLIF(@fecha_entrega_real, '');

Por qué funciona así: MySQL lee cada campo del CSV como texto en la variable temporal. NULLIF(x, '') convierte la cadena vacía en NULL; si tiene contenido lo inserta tal cual. Sin esto, MySQL insertaría '' (cadena vacía) en lugar de NULL, violando la semántica del campo.

1.3 Pregunta del Paso 3 — ¿Por qué precio_compra va en proveedor_producto?

Respuesta esperada: Porque un producto puede tener más de un proveedor y cada uno puede ofrecer un precio distinto. Si precio_compra estuviera en productos, solo podría guardarse un precio y se perdería la información sobre el proveedor más económico. La tabla proveedor_producto modela la relación muchos-a-muchos entre proveedores y productos, y almacena los atributos propios de esa relación (precio de compra, plazo de entrega, si es el proveedor principal).

2.2 Paso 8: ROLLBACK — Verificación

Después del ROLLBACK, ambas consultas deben retornar 0 filas:

SELECT * FROM ventas    WHERE cliente_id = 5;  -- 0 filas
SELECT * FROM despachos
    WHERE venta_id IN (SELECT venta_id FROM ventas WHERE cliente_id = 5);  -- 0 filas
Important

Para el docente: el error que produce MySQL es:

ERROR 1452 (23000): Cannot add or update a child row: a foreign key constraint fails
(`techstyle`.`detalle_ventas`, CONSTRAINT `fk_detalle_productos`
FOREIGN KEY (`producto_id`) REFERENCES `productos` (`producto_id`))

La transacción queda abierta pero marcada con error. El grupo debe ejecutar ROLLBACK manualmente. Si el grupo hizo COMMIT en lugar de ROLLBACK, el error FK lo impide de todas formas — el estado del venta_id vacío puede requerir limpieza manual.

Si alguien ejecutó ROLLBACK después de que MySQL ya hizo rollback automático del INSERT fallido pero antes de cerrar la transacción, el comportamiento es correcto: la venta de Diego no queda registrada.

2.3 Paso 9: Reflexión sobre transacciones — Respuestas esperadas

Situación ¿COMMIT o ROLLBACK? ¿Por qué?
La venta y el detalle se insertan, pero el stock de un producto llegaría a -1 ROLLBACK El CHECK stock >= 0 lanzaría un error que viola la integridad del negocio. No tiene sentido vender unidades que no existen. La transacción completa debe deshacerse.
500 productos nuevos, error de tipo en la fila 231 ROLLBACK A mitad del proceso el catálogo queda en estado inconsistente: algunos productos nuevos existirían y otros no. Es mejor deshacer todo y corregir la fila 231 antes de reintentar.
La devolución queda registrada pero falla el UPDATE de stock ROLLBACK El sistema quedaría en estado incongruente: la devolución dice que el producto volvió, pero el stock no lo refleja. ROLLBACK garantiza que ambas operaciones ocurran juntas o ninguna.
Tip

Concepto clave para reforzar: una transacción modela una unidad de negocio indivisible. La pregunta para decidir es: “¿Tiene sentido que esta parte del proceso ocurra sin que ocurra la otra?”. Si la respuesta es no → ROLLBACK.

4 Parte 4 — Síntesis y Reflexión

4.1 Paso 13: Modelo diseñado vs. modelo implementado

Dimensión Modelo en papel (W05) Base de datos real (W06–W07)
¿Se puede saber qué proveedor abastece un producto? Sí (diagrama) Sí — tabla proveedor_producto con FK a ambas entidades
¿Las FK impiden ventas de clientes inexistentes? En diseño Sí — ventas.cliente_id con ON DELETE RESTRICT lo impide en tiempo de ejecución
¿Un producto puede tener stock negativo? Según diseño, no No — CHECK (stock >= 0) lanza error si se intenta
¿Una venta incompleta puede quedar registrada? En teoría, no No — las transacciones garantizan atomicidad: o se registra todo o nada
¿Qué pasa si se borra un cliente con ventas? RESTRICT (diseño) Error bloqueante — MySQL retorna ERROR 1451 y rechaza el DELETE

4.2 Paso 14: Preguntas de diseño e implementación — Respuestas esperadas

Pregunta Respuesta
¿Por qué SET @variable = LAST_INSERT_ID() en lugar de poner el número directamente? Porque el número del ID lo genera MySQL automáticamente y puede cambiar si hay otras inserciones concurrentes o si el script se ejecuta en otra base con distinto estado del auto_increment. La variable captura el ID en el momento exacto de la inserción, haciéndolo portable y seguro.
¿Qué pasaría si dos vendedores insertan una venta para el mismo cliente sin transacciones? Podrían quedar ventas duplicadas o con datos parciales: uno puede insertar la cabecera de ventas mientras el otro inserta los detalles del primero en otra venta. Las transacciones + el aislamiento del motor impiden que una operación incompleta sea visible para otras sesiones.
¿Por qué precio_unitario se guarda en detalle_ventas y no se calcula desde productos.precio_venta? Porque el precio puede cambiar en el futuro. Si se consultara siempre el precio actual, todas las ventas históricas mostrarían el precio de hoy. Guardarlo en el momento de la venta garantiza que el registro refleje exactamente lo que el cliente pagó, lo cual es un requisito legal y contable.
Si TechStyle aplica un descuento general del 20%, ¿qué SQL ejecutarías? ¿Dentro de una transacción? UPDATE productos SET precio_venta = precio_venta * 0.80; — sí, dentro de una transacción, porque si el UPDATE falla a mitad (ej. error de conexión), algunos productos quedarían con descuento y otros no, generando precios inconsistentes.
Un cliente quiere borrar su cuenta. ¿Qué debe hacer Juan antes del DELETE? Primero verificar si el cliente tiene ventas asociadas (SELECT * FROM ventas WHERE cliente_id = X). Si las tiene, la FK con ON DELETE RESTRICT impedirá el borrado. Juan debe decidir con Roberto qué política aplicar: ¿anonimizar el cliente en lugar de borrarlo? ¿Archivar el historial? El borrado físico destruye trazabilidad financiera.

4.3 Paso 15: Análisis de impacto — Decisiones de negocio habilitadas

Capacidad implementada Decisión de negocio que habilita
FK con ON DELETE RESTRICT en ventas.cliente_id “Garantizamos que el historial de ventas nunca pierde la referencia al cliente — el dato histórico es inviolable para auditoría y contabilidad.”
CHECK stock >= 0 en productos “El sistema nunca registrará una venta de un producto sin existencia — elimina la posibilidad de vender ‘aire’ y los problemas de despacho asociados.”
Transacciones en el registro de ventas “Una venta queda completamente registrada o no queda en absoluto — no pueden existir ventas sin stock descontado ni despachos sin venta, lo que garantiza la coherencia entre el área comercial y la logística.”
Índice idx_ventas_fecha en ventas(fecha) “Las consultas de ventas por rango de fechas (reportes diarios, semanales, de temporada) responden en milisegundos incluso con millones de registros — Roberto recibe sus reportes de cierre en tiempo real.”
CHECK segmento IN ('Premium', 'Estándar', 'Básico') en clientes “Los datos de segmentación son confiables para las campañas de marketing de María — no puede existir un cliente con segmento ‘VIP’ o ‘elite’ que nadie definió, lo que garantiza que los filtros de campaña funcionen correctamente.”

4.4 Paso 16: Reporte para Roberto — Respuesta modelo

Para: Roberto Fernández, CEO TechStyle

De: Juan (DBA) — Asunto: Base de datos completamente operativa — estado al 2026-04-28

La base de datos techstyle está completamente poblada en MySQL Server. Contiene 9 tablas operativas con un total de 42 registros distribuidos de la siguiente forma: 10 categorías de productos, 6 clientes, 4 proveedores, 10 productos del catálogo, 4 ventas registradas, 5 líneas de detalle, 10 relaciones proveedor-producto, 4 despachos (2 pendientes, 1 en tránsito, 1 entregado) y 1 devolución en proceso. Las restricciones de integridad activas garantizan que no existan ventas sin cliente válido, stock negativo, precios en cero, ni segmentos de cliente fuera de los tres definidos. Gracias a las transacciones, cada venta se registra de forma atómica: si algo falla, el sistema deshace automáticamente la operación completa. A diferencia de Excel, el sistema puede responder en segundos preguntas que cruzan múltiples áreas del negocio (margen por proveedor, estado logístico por cliente, devoluciones pendientes). Los siguientes pasos son implementar la lógica de consultas analíticas, conectar un frontend para el equipo de ventas, y definir una política de respaldo de datos.

5 Errores frecuentes y cómo evaluarlos

Error Severidad Orientación docente
Loading local data is disabled Procedimental No penalizar si el grupo usó el INSERT alternativo y los datos son correctos.
Columnas mal mapeadas en LOAD DATA (campos en el orden incorrecto) Medio Los datos quedan en columnas incorrectas. Verificar con SELECT * FROM tabla LIMIT 5.
ROLLBACK no ejecutado después del error de FK Conceptual Indica que el grupo no comprendió que la transacción queda abierta. Reforzar el concepto de “transacción abierta vs. cerrada”.
COMMIT después de un error de FK Conceptual MySQL rechaza el COMMIT cuando hay un error pendiente (ERROR 1213). Aprovechar para explicar el comportamiento del motor.
precio_unitario sacado de productos en lugar de guardarse en detalle_ventas Diseño Indicar que el precio cambia en el tiempo y el historial perdería precisión.
Hardcodear venta_id = 4 en lugar de usar @venta_sofia Estilo Aceptable si el resultado es correcto; señalar por qué es frágil en producción.
